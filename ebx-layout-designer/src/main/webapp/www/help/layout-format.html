Layout format ebx-form-layout/1

A layout is one JSON document, stored in field layout of LayoutDesigner/FormLayout (one row per model and table, version increased at each save). The designer writes it; this page is for reviewing, diffing or generating one.

Conventions

  • Paths are relative to the record and start with /: /Identification/Name, /Address/City. An association is named by its path too (/orders).
  • Texts are objects with one entry per locale: {"en-US": "Overview", "fr-FR": "Vue d'ensemble"}. A missing locale falls back on the instance's default locale, then on the first text written.
  • id identifies a block inside the layout (used for anchors and "Go to field").

Document

{
  "format": "ebx-form-layout/1",
  "name": "Customers (B2C)",
  "model": "urn:ebx:publication:B2CCustomers",
  "table": "/root/Customer",
  "locales": ["en-US", "fr-FR", "it-IT"],
  "tabs": [ … ]
}

model is the schema location: urn:ebx:module:<module name>:/WEB-INF/ebx/schemas/X.xsd for a module model, urn:ebx:publication:<publication> for a DMA model.

Since 1.10.0 the document may also hold personal, adminSeesAll and variants: see Who sees what below.

facts: items (paths), count (path of an association whose rows are counted).

validation: sev ({"error": true, "warning": true, "info": true}), group (severity, tab, none), max (messages before "more"), links (Go to field), hideEmpty, actions (array of {"on": <path>, "btn": <text>, "go": <path>}: a button labelled btn shown when a message is about on, opening go), covers (paths of fields this block stands for).

grid: a (association path), style (native or cards), cardFields (paths shown on each card), addBtn (text). Since 1.14.0 a native grid outside the first tab is lazy unless "lazy": false. Since 1.11.0, lazy: true builds the native grid only when its tab is first opened, in a frame (module service LayoutGrid), and height (pixels, default 460) is its height until the frame fits its content.

map: lat, lng (paths), tall (larger map), and since 1.7.0 address (paths, in order: number, street, postcode, city, country…). When latitude or longitude is empty, the non-empty address values (a foreign key gives its label) are joined with ", " and the EBX server asks a Nominatim search service for the position: OpenStreetMap's public one by default (at most one call per 1.1 s, failures retried after ten minutes). Since 1.15.0 the form never waits for it: an address not known yet is looked up in the background and the map shows at the next opening, or at once when the user clicks Locate now (since 1.15.1: the browser asks the module's /geocode address, with a ticket signed by the form); positions found are kept in <ebx.home>/layout-designer-geocache.tsv (property ebx.layout.geocoder.cache, off to keep them in memory only). The system property ebx.layout.geocoder.url names another Nominatim (self-hosted), or off to never send an address out. The map then says "position from the address …"; an unknown address shows a link to OpenStreetMap's search. Map computed from the address: each unknown address is looked up in a geocoding service (at most one request a second on the public service) and kept in a cache. For many records, add latitude and longitude fields to the table and choose them in the block. A table of more than 1,000 rows placed by its address gets one WARN line in kernel.log (1.15.1).

tree: parent (path of the parent foreign key), children (association path).

hours (opening hours, read only): whether the record is open now in its own time zone, the current week (one card per day, today highlighted) and the next exceptional days. Every table and field comes from the block; rows are read through the record's associations.

Key Meaning
week.a association of the regular hours (required)
week.day, week.open, week.close fields of the association's table: day, opening time, closing time
week.closed optional boolean field: the row means "closed"
days optional, the day field's code for each ISO day: {"1": "MON", …, "7": "SUN"}. Empty: the code is recognised by itself — 1 to 7 (Monday = 1), English, French or Italian day names, full or abbreviated (MON, MONDAY, LUN, LUNDI, LUNEDÌ…), case ignored
exceptions.a optional association of the exceptional hours; absent: no exception section, only the regular week counts
exceptions.date, .open, .close, .closed, .reason fields of that table (date, times, optional closed flag, optional reason)
max upcoming exceptions listed (default 3; 0 hides the section)
tz optional field of the record holding a time-zone id (Europe/Paris); absent or unknown: the server's zone
excTitle optional text: title of the exceptions section (default "Upcoming exceptional hours")

Times: a text HH:mm (also H:mm, HH:mm:ss, 24:00) or a time value. Dates: a date value or an ISO text. A day may hold several rows (split hours); a slot whose closing time is before its opening time ends after midnight. A row marked closed, or with a missing time, adds no slot; a day with no slot is shown "Closed". An exception replaces the regular hours of its date. On creation the block says the hours are entered once the record exists.

Blocks added in 1.24.0: effective-dated models

For models where an entity (a fund, a contract, an organisation) is a stable identity whose values live in successive states, each from an effective date to an end date (inclusive; empty = open-ended), with the link to the parent carried by the state. Worked example: the ROSA fund repository (Fund → FundState, SubFundState.fund, ShareState.subFund).

Since 1.26.0 every link of these three blocks (an entity, a state, a row of a delta report) opens the record in EBX's own modal pop-up, a sub-session of the form (the table views' preview mechanism): the user stays on the form, on the chosen date, and comes back to it on close; a middle click still opens a new tab. Planned: an inline summary of the state under its line (fields configured per level), before opening the full record.

Permissions, as for every block: a state the user may not see (record permission) is left out, and so is a state whose key to the parent, key to the entity or effective date the user may not read (field permission); every value shown goes through the field permission. A delta report is one text field: whoever may read it reads the values it holds, whatever the permissions on the fields it names. Cost: asOfTree runs one scan of each level's states table (an OR of the parents' keys, 100 per query; 2,000 states per level at most, then a note), stateTimeline one association read or one scan, delta none; every tab of a form is rendered when it opens, so keep these blocks on tables where a tree is a few hundred states (ROSA: 6,572 sub-fund states, 15,100 share states, a scan of 20-25 ms).

Type Keys
asOfTree levels[], one per level under the root: states (the children's states table, /root/SubFundState), parent (its foreign key to the parent entity, ./fund), identity (its foreign key to the child's own entity, ./subFund), effectiveDate, endDate, label (a field of the state; empty: the state's label), chip (a field shown as a badge: status, code), name (text per locale: what the count calls the level's entities; empty: the label of the entity table the identity key points to, without a trailing parenthesis). root: a foreign key of the record to the root entity (empty: the record itself; on a state, ./fund). selfStates + selfIdentity, selfEffectiveDate, selfEndDate, selfLabel, selfChip: the root's own states. date: a date field of the record giving the default date (empty: today). Every state of every entity is read (500 per table and per parent at most) and put in the page; the date input, the ◀ ▶ buttons (previous / next change among all effective and end dates) and Today decide which state each entity shows, with a count per level. Since 1.25.0 the date follows the user: without a date field, the block opens on the date last chosen in an explorer with an "in force on" date or in another block (sessionStorage key ldfAsOf:<user>), and a date chosen here is shared the same way. An entity with no state at the date is greyed, and hidden when none of its descendants has one either
stateTimeline the states of one entity on a time scale: a (an association of the record to its states) or, when the record is itself a state, via (its foreign key to the entity: its siblings are drawn and the record's own state highlighted). effectiveDate, endDate (empty end: the band runs to the edge, faded), label, badge + colors (tone per value, e.g. the source or the project; without colors, one tone per value met), date (a date field of the record drawn as a dark marker, besides today's red line). Month, quarter or year ticks by span; each band and label opens the state
delta a before/after report kept as JSON in a text field: field of the record, or of each row of a (one section per row, titled by label, with the count of changes). Shapes read: an object {"name": {"before": "…", "after": "…"}}; an array of {"field"|"path"|"name", "before"|"old"|"from", "after"|"new"|"to"}; either of them under a changes, fields, items or delta key. labelsFrom: the table whose field labels name the keys (empty: this table; a key may be name, ./name or /root/T/name); max (50). A text that is not JSON says so; an empty report says "No change recorded"

Behaviours (1.4.0)

A condition is {"field": path, "in": [values]}, or "notIn", or {"field": path, "filled": true}, or "empty": true. Values are compared as stored: an enumeration's code, a foreign key's key, true/false.

Where Key Effect
block showIf the block shows only while the condition holds, live; on a panel onHide: "clear" empties its fields when it hides
field showIf, onHide the same for one field of a panel
field mandatoryIf the mandatory asterisk follows the condition, live (ebx_form_setMandatoryIndicator)
field readOnlyIf read only when the condition holds, and/or for roles, never for exceptRoles; computed when the form opens
panel attributesBy {table, key, familyCol, attributeCol, mandatoryCol, hideEmpty}: a table of the same dataset says which fields go with each value of key (a family); a field the table lists shows only for its families (mandatory when mandatoryCol is true), a field it never lists always shows; hideEmpty (true) hides the panel with no field left. The attribute column holds a path (/Dimensions/length) or a field name. Families in a tree: familyParent (field of the families table holding the parent family) and familyTable (default: the table key points to); a sub-family then also gets its ancestors' attributes, the closest level deciding mandatory

The live part uses the documented JavaScript API of EBX forms (ebx_form_getValue, ebx_form_setValue, ebx_form_setMandatoryIndicator), called after each change of the controlling field (UIAtomicWidget.setActionOnAfterValueChanged); the first state is computed on the server. A behaviour changes what is shown, never what EBX validates: a value that must be mandatory needs a rule in the model.

Who sees what (1.10.0)

By default everyone sees the whole form, as before 1.10.0. Three optional layers:

Roles of a tab, block or field. roles: visible only for these roles; roRoles: read only for these roles. Values are role names as in the directory ("Acheteur"), "administrator" for the built-in one. A user who has none of the roles does not get the item at all (a tab with it, a panel whose fields are all hidden, a row left empty); a user who has one of the roRoles gets it read only (a panel or tab read only makes its fields read only). Administrators see everything and keep their rights, unless the document says "adminSeesAll": false.

{"id": "com", "label": {"fr-FR": "Conditions commerciales"}, "roles": ["Acheteur", "Comptabilite"], "rows": [ … ]}
{"type": "panel", "id": "pay", "roRoles": ["Acheteur"], "fields": [{"p": "/Iban", "roles": ["Comptabilite"]}]}

Variants. variants is an array of whole forms for some roles, in priority order; a user gets the first variant one of whose roles they have, else the standard form (tabs). A variant holds id, name (text), roles and its own tabs, which take the same keys as the standard ones. A variant without roles is never used.

"variants": [{"id": "req", "name": {"fr-FR": "Demande de création"}, "roles": ["Demandeur"], "tabs": [ … ]}]

Personal arrangement. "personal": true lets every user arrange the form for themself ("Arrange my form", a button on the form and an entry of the record's Actions menu). Each user's arrangement is one row of LayoutDesigner/UserFormPreference (key: user, model, table, variant id — std for the standard form), its prefs field a JSON object laid over the layout, never a copy of it:

Key Meaning
tabs tab ids in the user's order; a tab not listed keeps its place
defaultTab tab opened first
hiddenTabs, hidden tabs and blocks (ids) not shown
collapsed blocks folded under their title
pinned blocks moved, in this order, to a first tab "My essentials"

A tab or block with "locked": true can be neither hidden nor moved by a user. While a record is created nothing is hidden or folded. A preference naming a tab or block that no longer exists is ignored, and a block added later appears at its place for everyone.

None of this is security: a field left out of a form stays readable in the table view, an export or the APIs. EBX permissions protect the data.

Validation (1.17.1)

The layout field of FormLayout carries a constraint (com.on.ebx.layout.designer.LayoutValidation, bean property checks = all or off) that never blocks a commit and is re-checked at every validation. It reports: invalid JSON (error); the table no longer in the model (error); a path of a block, a field of a panel or the field of a showIf/mandatoryIf/readOnlyIf found neither on the record nor on a linked table (error); a component no longer registered, a wf.pub or a workflow button's publication no longer published, a model with no dataset on the instance (warning). The runtime itself skips such references silently.

Example

{
  "format": "ebx-form-layout/1",

actions (since 1.14.0)

Buttons on the record. items: a list of buttons, each with label (localized), and either workflow (a publication to launch) with var (the data context variable that receives the record's XPath), or service (module@Service, opened on the record in EBX's pop-up). Optional: tone (ok, warn, bad, info, accent, muted) and cond (an XPath predicate on the record; false hides the button), single (true: while an instance launched with this record's XPath in var is still running, the button opens its task, shown without being taken, instead of launching another). A workflow button shows only to a user who may launch the publication; it opens the module service LayoutAction in EBX's pop-up, which asks for confirmation, launches as the user and opens the first task, inside the perspective the form was opened in. The service reads the button again from the layout as the user sees it (never from the address), and since 1.23.1 tests again, before launching, what decided its drawing: cond on the record, wf and session, as well as the right to see the block and to launch the publication. A button hidden by one of them cannot be launched by typing the address of the service: the user gets "this action is no longer available for this record" and nothing is launched. The first task is looked for once, about a second after the launch; when it is not there yet the user is sent to the inbox (the work appears there), the request never waits longer. Nothing is shown while a record is created, and a block with no button the user may use is not drawn.

Conditions tied to workflows (since 1.17.0)

Any block, and any button of an actions block, may carry "wf":

Key Values Effect
ctx outside, inside shown only when the form is NOT opened from a workflow task, or only when it is (Session.isInWorkflowInteraction(true))
running hide, show hidden, or shown only, while an unfinished workflow instance holds the record's XPath or primary key in one of vars
pub a publication name restricts running to that publication; empty: every publication
vars variable names, comma separated the data context variables that point to the record (tiersXPath…)

Example: the "Change bank details" button hidden inside any workflow task and while a bank-details change is running for the supplier: "wf": {"ctx": "outside", "running": "hide", "pub": "FournisseursChangementRIB", "vars": "tiersXPath"}. The running instances are looked up once per display and shared with the Workflows in progress block.

Conditions on the user's session (since 1.23.0)

Any block, any field of a panel and any button of an actions block may carry "session", read in the EBX session of the user who opens the form: its tracking information (Session.getTrackingInfo()) and its attributes (Session.getAttribute(name)), whatever set them in that session (a workflow task, a trigger, a user service).

Key Values Effect
trackingInfo.op equals, contains, notEquals, notContains, filled, empty compares the tracking information with trackingInfo.value; no op: no condition on it
attribute.name an attribute name the session attribute to read; empty: no condition on attributes
attribute.op the same operators, filled by default compares the attribute's value with attribute.value

A session condition arranges the display, it protects nothing. The tracking information is not only set by the server side (a task, a trigger, a service): EBX's web component accepts a trackingInfo parameter in its address (UIHttpManagerComponent.setTrackingInfo, public API), so a user may be able to choose the text a trackingInfo condition compares. (That this parameter reaches Session.getTrackingInfo() inside the form has not been measured yet: treat it as possible.) A session attribute (attribute) cannot be typed in an address, so prefer it for a condition that must hold. What must really be refused belongs to EBX permissions, not to a display condition; since 1.23.1 a workflow button does re-test its session condition when it is launched, which narrows but does not remove this limit.

Both parts must hold. Texts are trimmed and compared ignoring case; an attribute holding a collection or an array matches when one of its values does, any other object is read through its text. The session is read when the form is drawn, like the roles: a value set while the form is open shows at the next display. An item whose condition fails is not drawn at all; for a field this is display only (EBX's own validation still applies).

Example: the purchasing panel shown only while the session carries the attribute etape = validation_achat, and the "Reject" button hidden when the tracking information says the record comes from an import: "session": {"attribute": {"name": "etape", "op": "equals", "value": "validation_achat"}} on the panel, "session": {"trackingInfo": {"op": "notContains", "value": "IMPORT"}} on the button.
