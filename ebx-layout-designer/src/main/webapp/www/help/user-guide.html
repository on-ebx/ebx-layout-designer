Layout Designer: user guide

The Layout Designer lays out the record form of an EBX table by drag and drop, with no code and no compilation. It is for administrators. Business users only see the result: the record form of the table.

1. Start a layout

From the list of layouts: the Record form layouts page (dataset LayoutDesigner, table Form layouts, Actions › Record form layouts, or its entry in a perspective) lists the saved layouts: table, model, version, state, last change. Open the designer opens one on a dataset of its model.

To start a new one, choose the dataspace and the dataset with EBX's own selectors (tree and search), then the table (the list follows the chosen dataset), then Continue.

From the table itself: open the table, Actions › Design the record form.

The first time, the designer proposes a starting layout built from the model: a General tab with one panel per group of the model (two columns), the loose fields in a first panel, and one tab per association. It is a draft until you save it.

2. The screen

3. Building the form

  • Tabs: + Tab, drag a tab to move it. The inspector sets its label (one per locale) and a counter: the sum of the rows of the ticked associations, shown in the tab title ("Orders (5)").
  • Rows: + Row with 1 column or 2 columns, with proportions 1:1, 2:1 or 1:2. Under 900 px a two-column row stacks, left column first.
  • Fields: drag a field into a panel. Dropped on an empty column, it creates a panel around itself. Per field: a label for this form (empty = the model's label, translated by EBX), a widget, read only, label above on the full width. A mandatory field left off the form is flagged: creating a record without it would fail.
  • Associations: drag one to place its grid.
  • Blocks: drag from the palette; drop between two rows to open a new row. A block dropped on a tab goes to its end.
  • Removing: select a block or a field and press Del (the delete key, Backspace on a Mac keyboard), or drop it on the bin at the bottom right of the window. Undo puts it back.
  • Every change says what it did ("panel X was created around Y") and Undo takes it back.

Widgets of a field

The list offers only the widgets that suit the field's type, in two groups.

  • Input: text, single-line text, text area, number, date, check box, Yes / No (radio), drop-down list, list without "Create" (foreign key), radio buttons. EBX's own widget is used when nothing is chosen.
  • Display (read only): highlighted figure, pill, link, code, and since 1.4.0 pill coloured by value, amount with currency, value with unit, percentage bar, star rating, relative date ("in 12 days"), duration, country (name and flag), phone and e-mail (with Copy), web address, colour, EAN / GTIN barcode (bars and check digit), copyable identifier, tags, masked value (some roles may show it all), link to the record of a foreign key, thumbnail, GPS coordinates, yes / no as an icon. Their settings (currency, unit, colours per value…) appear under the list. Choosing one ticks Read only. Since 1.4.4 a display widget always makes the field read only on an existing record (a layout saved earlier without the box ticked shows it too); while a record is created the field keeps EBX's input.

Behaviours of a field

Under Behaviours in the field's inspector:

  • Show only if (live): the field appears or hides while the user types in another field, without saving (Family is one of Wipers, Opt-in is filled…); its value can be kept or cleared when it hides;
  • Mandatory if (live asterisk): the asterisk follows a value;
  • Read only if: for some values of a field, and/or for some roles, except for others (computed when the form opens).

A behaviour changes what is shown, not what EBX validates: to block saving, add a rule to the model.

  • Load a grid when its tab is opened (inspector of a grid block): the form opens faster when it holds several native grids; the grid is built, in a frame, the first time its tab is shown, with its own toolbar and "+".

Settings on every block: Show only if (live), a condition on another field evaluated while the user types (on a panel, the hidden fields' values can be cleared); Show only if (XPath, when opened), a predicate on the record (./Lifecycle/status = 'ACTIVE'); Hide when creating a record.

A panel can also take its fields from a configuration table of the dataset: Fields driven by a configuration table names the table, the field of the record that drives (a family), and the table's columns for the family, the attribute (path or field name) and, optionally, mandatory. A field the table lists for a family shows only for that family, live; a field it never lists always shows.

A row can be a collapsible section (row inspector): a title, open or collapsed when the form opens.

5. The validation report block

It shows the record's own validation report, as EBX computes it from the model's constraints and rules: nothing to configure on the data side.

  • choose the severities shown (errors, warnings, information), the grouping (by severity, by tab, none) and how many messages show before "more";
  • each message says where the field is on this form (Overview › Loyalty › Points) and, with Go to field, opens the right tab and highlights it;
  • action buttons: a button shows only when a message is about the chosen field, group or association, and opens the place where it is fixed (for example Add an address on a missing e-mail-invoicing address);
  • Hide the block when the report is empty.

Messages come in the user's language. A message written in one locale only (a DMA validation rule typed in English) shows in the instance's default locale, then in English.

6. Languages

Every text you type (tab labels, titles, notes, button labels, help texts, field labels) has one value per locale of the instance. Choose the locale in Language and type; a dotted underline marks a text with no translation in the language shown. Translations lists every text of the form with what is missing per locale, and Only texts to translate narrows it. A text missing in a locale shows in the default locale. Model labels and validation messages are EBX's own and are already translated.

The designer's own screens are in French or English, after the user's locale.

7. Who sees what: roles, variants, personal form

By default everyone sees the whole form, as before 1.10.0. Nothing needs setting when it is not useful; then three levels, from the lightest to the most complete:

  1. Restrict a part. Select a tab, block or field: the Who sees it part of the inspector has two lists of roles, Visible for (empty = everyone) and Read only for. Roles come from EBX's directory; another name is typed in the field below (LDAP or SSO directory). A hidden tab takes its blocks with it, a panel whose fields are all hidden disappears. A mandatory field hidden for a role prevents that role from creating a record: the designer says so.
  2. A variant for a role. Form › + New variant (or Profiles and variants › Duplicate as a variant) copies the form being edited; give it a name and the roles that get it, then edit it like any other. When a record opens, each user gets the first variant they have a role for (the order is set in Profiles and variants), else the standard form. Example: a one-tab "Creation request" form for the requester.
  3. The personal form. Tick Users can arrange their form in Profiles and variants: a button Arrange my form appears at the top of the form (and in the record's Actions menu). Each user reorders the tabs, picks the tab opened first, hides or folds a block, or pins it to a first tab My essentials. It is never a copy: a later change made in the designer reaches everyone, a new block appears at its place. Tick Always shown on a tab or block that must stay (e.g. blocked payments). While a record is created nothing is hidden or folded. Back to the standard form clears the user's arrangement.

Preview as (at the top) shows the form of a role or of a user of the directory: in Design mode what they do not see is struck through and greyed; in Preview mode it disappears, and the form switches to the variant they would get. Profiles and variants lists the variants, who gets which form and the Who sees what table (a click on a row selects it).

Administrators see everything (an option can turn that off). This is not security: a field left out of the form stays readable in the table view, an export or the APIs; EBX permissions protect the data.

8. Save, declare, use

  • Save writes the layout (JSON) as a new version in LayoutDesigner/FormLayout. It shows at the next opening of a record, no restart, as soon as the table declares the designed form.
  • Activation (the banner under the header, since 1.9.0: orange = not used yet, blue = waiting for the restart, purple = DMA model, green = active and last drawn on a given record; See the steps opens the guide):
  • model packaged in a module: Activate writes the recordForm line in the XSD, with a backup; restart the server once, then open a record to check. Put the previous form back undoes it (restart again);
  • DMA model, four steps in the model screen: declare com.on.ebx.layout.runtime.ConfigurableForm in the model's Component library (Component name, Configuration › Rule; EBX infers the UIForm type), choose it for the table in Form layout › Component, publish the model, open a record to check. No restart. The data-model MCP operation set_form_layout does the first two steps;
  • when the designer cannot write the module's XSD (folder not found), the guide gives the line to paste by hand.
  • </> Code: the saved JSON, and the same layout as a frozen UIForm class for a project that does not want the designer at run time (optional).

9. For developers: registered components

A module can add its own block. Implement com.on.ebx.layout.runtime.LayoutComponent (getLabel(Locale), write(UIFormPaneWriter, UIFormContext, JsonNode block, Locale)) and register it once at start:

LayoutComponents.register("acme.creditScore", new CreditScoreComponent());

It then appears in the palette under Registered components; the runtime opens a panel with the block's title and note, and the component writes inside it. The module needs the runtime jar on its compile classpath only (it is on the server's at run time).

10. Limitations

  • DMA models: the designer cannot write the declaration itself (declare the class in the model screen or with set_form_layout), nor read it: the state in the top bar then says DMA model: check the declaration. The state of a module model comes from its XSD file; a declaration applies after the next restart.
  • Go to field needs a message attached to a field. A rule declared on the table (a constraint across several fields) reports on the record as a whole: the message shows, without a location or a link. An action button tied to a field therefore never shows for such a rule.
  • A field-level rule is not evaluated by EBX on an empty field: a rule "e-mail or mobile" belongs on the table.
  • The map is OpenStreetMap only (an iframe): it needs the user's browser to reach openstreetmap.org.
  • A condition that cannot be evaluated (a wrong XPath) shows the block and logs a warning in kernel.log.
  • One layout per table and model: every dataset of the model shares it.
  • Behaviours run in the browser and change only what is shown: EBX's validation is unchanged.
  • The change history block needs history activated on the table; Linked record, Hierarchy and Link to the record open the target in a new tab.
  • Previews of the blocks that read an association's rows are indicative in the designer; the form shows the real values.
  • Seen running on EBX 6.3.0-rc2 only, with the locales en-US, fr-FR and it-IT.
